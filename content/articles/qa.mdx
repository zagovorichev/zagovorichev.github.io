The core purpose of Quality Assurance is to prevent mistakes and defects in the development and production

### Attributes

- Functionality. <Muted>How well it works according to technical specification</Muted>
- Availability. <Muted>Amount of time the application software is available to users</Muted>
- Performance. <Muted>How quickly the application completes required functions.</Muted>
- Testability. <Muted>How easy it can be tested.</Muted>
- Security. <Muted>possible breaches or catastrophic losses.</Muted>
- Usability. <Muted>How simple is UI (User Interface)</Muted>
- Reliability. <Muted>How stable the system is</Muted>

### QA building blocks

- Quality Assurance. <Muted>From development to delivery.</Muted>
- Quality Control. <Muted>Part of QA ↑. Quality of software.</Muted>

## QA Implementation

### Benefits

How to ensure management to use testing.

- Product Quality. <Muted>QA allows to check complete functionality, how it works on multiple devices, platforms. It controls amount of bugs.</Muted>
- User Experience (UX). <Muted>Aimed at exploring user expectations.</Muted>
- Reducing the Costs of Bugs. <Muted>Finding bugs as early as possible will cost cheaper than fixing them after deployment.</Muted>

## Types of Testing

Developers and test engineers should be familiar with each type since each is necessary to ensure an application’s success.

### Manual Testing

Manual testing is a software testing process in which test cases are executed manually without using any automated tool. <br/> Good: identify defects that automation tools may miss. <br/> Bad: may be difficult, take a lot of time, boring, repetitive, less accurate than automated.

### Automated Testing

Automate routine operations. <br/> Good: Reduce cost of repetitive manual tests, increase accuracy. <br/> Bad: Cannot be applied to every aspect of testing. Limited by tools of auto-testing.

### Functional Testing

Checks that the system works as expected by the business requirements. Can be manual and automated.

### Non-Functional Testing

Verifies performance, usability, reliability...

## Testing Methods

**White box, structural testing, unit tests** Unit-Level of testing. Can uncover structural problems, hidden errors and problems with specific components.

**Black box testing** checks that the system as a whole is working as expected.

**Grey box testing** integration testing, end-to-end system testing, and penetration testing \[pen test, is a simulated cyber attack against your computer system to check for exploitable vulnerabilities\].

## Characteristics of failure

- Errors. <Muted>Made by a developer while writing the code, including any possible misunderstandings of the requirements or intended functionality.</Muted>
- Failures. <Muted>The application code is not functioning or is unable to function as expected.</Muted>
- Defects/Bugs. <Muted>The code does not produce an expected result.</Muted>

## Testing Documentation

Allows developers and specialists to keep each testing artifact stored and cataloged accurately.

### Test Plan

Focuses on the "what" and the "when" of testing.

Have include

- A project-specific impact on testing
- The scope of testing
- Quality and acceptance criteria
- Risk management
- The test team, test schedule, and test deliverables

### Test Strategy

Focuses on the "how" of testing.

Can include

- How the team will organize testing
- Which testing types will be in scope to address product risks
- Which test design and execution approaches the team will use for a testing type

## Test case management

Correct test case management decrease duplication of tests, adds standards of testing, centralize metrics and reports, provides history of changes, verify test completion, documentation.

- Test Case. <Muted>Steps to verify that it works.</Muted>
- Test Suite. <Muted>Collection of test cases to verify functionality</Muted>

  - **Sanity** Checks if the bugfix fixed the bug.
  - **Smoke** Checks basic functionality.
  - **Regression** Checks existing functionality (to verify that changes don't break anything).
  - **UI** Checks how user interacts with app.
  - **Performance** Checks and measures the performance of the system under different loads
  - **API** Checks functionality, performance, security of API
- Test Plan. <Muted>Scope of testing, resources, complete timeline of test activities.</Muted>

### Test Case Life Cycle

The test case life cycle documents each step you will take before and after writing your test cases.

- Requirements analysis. <Muted>Getting all the data that we need for test creation (Environments to run tests on, tools, income data for the test).</Muted>
- Test Case.
- Mapping. <Muted>Map requirements to test case to verify that all requirements covered with test case.</Muted>
- Review.

  1. Self-Review. Test should be created according to SRC (**Software Requirement Specification**) describes the software’s purpose and FRD (**Functional Requirements Document**) is similar to a contract stating the functional requirements needed for software to meet agreed-upon capabilities.
  2. Peer Review. Another tester reviews it.
  3. Supervisor Review. If lead/architect should review it.
- Execution. <Muted>Run test case (define how and who should run the test and run it).</Muted>
- Regression testing. <Muted>Run all other tests to check that this functionality doesn't break anything else.</Muted>
- Test Case Inspection. <Muted>Review all tests to identify duplications.</Muted>

Peer review or Self-review, what to check?

- Functionality Coverage. <Muted>Check that test case covers full functionality that should be checked.</Muted>
- Spelling.
- Grammar.
- Template/Standards. <Muted>All test cases should have the same standard view.</Muted>
- Clear description in common for all testers words.
- Duplication.
- Obsolescence. <Muted>Test could be redundant or obsolete and must be removed.</Muted>

### Test Coverage

Metric that shows how many requirements have tests.

**Requirement Test Coverage Report**

- Status of the testing. <Muted>Passed and Failed test cases.</Muted>
- Track which requirement are covered with what test cases.
- Track requirements without tests.

**Requirement Traceability Matrix**

- Document that delivered at the conclusion of SDLC.
- All requirements and test cases to them.
