Software development has not a big but really fast history, so there are a lot of tools, practices, documented solutions.

## Quality of the code.

**High-Quality Code** — The code with both Functional and Structural high quality.

### Functional Code Quality

What code Does? Includes Unit and Functional Tests.

### Structural Code Quality

How code Looks? Code review and Static code analysis.

- Clear.<br/><Muted>Code looks like a poem, and when anyone reads it he can understand what it is all about.</Muted>
- Maintainable.<br/><Muted>It's easy to add new code or change the old one.</Muted>
- Standardised.<br/><Muted>The same code style for everyone.</Muted>
- Testable.<br/><Muted>Each feature can be tested independently.</Muted>

## Coding Standards.

- Style Guide. <br/><Muted>A style guide is responsible for visual representation of the source code and it depends on the programming language. This doesn’t usually include any information about naming and design patterns.</Muted> <br/><Muted>How code looks: layout; how to use whitespaces/tabs in the code; names of variables, functions, classes, etc.</Muted>
- Principles. <br/><Muted>Coding principles are responsible for source code structure to ensure its readability and modifiability.</Muted> <br/><Muted>Design (SOLID, KISS, YAGNI, Patterns, etc.); Code structure (lines in methods, parameters in functions, etc.); Language constructions (Exceptions, breakouts, conditions usages).</Muted>
- Project specific Conventions. <br/><Muted>Project-specific code conventions explain project-specific implementation and extended coding principles.</Muted> <br/><Muted>Everything else, that helps to write the code in the consistent way.</Muted>

## Code Quality Metrics.

Each developer has own high-quality metrics. But there are metrics that allow to have standards for everyone.

- Cyclomatic Complexity.<br/><Muted>Measures the structural complexity of code. It refers to the number of decisions in the source code. The higher the cyclomatic complexity, the more complex the code.</Muted>
- Class Coupling.<br/><Muted>How many classes a single class uses. The lower the value, the better. Good software design requires low coupling; designs with high coupling are difficult to reuse and maintain.</Muted>
- Class Hierarchy, or a Depth of Inheritance Tree (DIT).<br/><Muted>complexity of the class hierarchy in object-oriented programming. It shows how object classes are derived from other classes. The higher the DIT, the more complex the software.</Muted>
- Duplications.
- Method Cohesion.<br/><Muted>A method should explicitly state why it is written. Otherwise, it lacks cohesion. High cohesion means that methods of the class are codependent and form a logical whole, whereas low cohesion results in huge classes that are difficult to understand and maintain.</Muted>

### Example of Code Quality for the team

- Onboarding for newcomers.
- Agreement of the how code should be developed.
- Processes and tools in place for testing to ensure coding standards.
- A style guide to keep everyone’s code clean and consistent.
- Documentation of any project specific information.
- Coding principles for the project.

## Testing

**The Scope of Testing** — what areas, features, and functionalities of an application should be tested.

### Testing levels

- Unit tests.<br/><Muted>Least time and cost. Test only the small function without any dependencies.</Muted>

- Integration tests (API Tests, External Web Integration Tests, or Component Tests). <br/><Muted>Interaction of a piece of code with external components.</Muted>
- UI Tests (End-to-End Tests, Acceptance Tests).<br/><Muted>The most heavy tests, to test it we should run an application.</Muted>

### Unit Tests

> 77% of the failures can be reproduced by a unit test.

**Unit Test** — is a short program fragment written and maintained by the developers on the product team, which exercises some narrow part of the product’s source code and checks the results.

**Maintainability** — is the ability to change, understand, and test an application easily. Unit tests make code easier to change, to understand, to test.

Exceptions. Proofs-of-concept (POCs) or conference demos―and projects with a very short timeline (less than three months).

### F.I.R.S.T. from Robert Martin

- **Fast**
- **Independent** <Muted>Works independently in different order with others.</Muted>
- **Repeatable** <Muted>In any environment.</Muted>
- **Self-Validating** <Muted>Only one logic to be tested by the test.</Muted>
- **Timely** <Muted>Created before or at the same time with the code.</Muted>

### Code Coverage

One hundred percent unit test coverage is not enough to guarantee high code quality.

Code coverage is a metric that shows how many rows of code were run and the total numbers of lines in the code.

## Code Review

The process when team members check the code written by other team members. Follow the coding standards. Validate business logic. Validate unit tests for changed logic as a part of the code review process.

## Knowledge Sharing

### Goals of the knowledge sharing

- Maintain the project
- Share standards and best practices
- Right priorities for every team member
- Decrease time of one to one knowledge sharing

### Software Development Life Cycle

- Different reviewers for pull requests.
- One developer never works on the same kind of tasks.
- Always update Knowledge Base, not after but at the same time when you develop/update a feature.

### Knowledge Base

<Muted>Confluence, Wiki, etc.</Muted>

- The project goal and description.
- The team structure and roles.
- Links to environments.
- Standards and practices.

### Onboarding

- Newcomers Guide. <Muted>Small TODO list with information what to do and in what order (create email, create account, configure authenticator, etc.). The List of goto persons (the table with contacts of someone who can solve something). Links or instructions of how to install the project.</Muted>
- Small demo. <Muted>Someone from the team can show and explain general picture of the project.</Muted>
- Mentor. <Muted>Someone who can help at the first time in the project.</Muted>

## Technical Debt

Technical Debt is the implied cost of additional rework caused by choosing an easy (limited) solution now instead of using a better approach that would take longer.

Consist of 2 parts:

- Dept itself
- The interest (extra efforts to work with code because of the debt)

There are 2 kinds of tech debt

- Intentional. <Muted>When everyone knows why do we need that (f.e. Proof of Concept - POC, or a Minimum Viable Product - MVP, or meet deadline to publish feature).</Muted>
- Unintentional. <Muted>Lack of tech knowledge, project process issues.</Muted>

### Technical Debt Indicators

**Delivery**

- Quality Degradation. <Muted>Production defects and bugs; Regression, when bugs appears in different part of the system during the regression tests; A list of known issues.</Muted>
- High Cost of System Change. <Muted>Adding new features should not take longer as the project grows.</Muted>
- Spikes and POC's in limited timeline. <Muted>If during these tasks we met a lot of issues and side effects.</Muted>
- If only couple of team-members can do feature/changes or it is hard to understand the project for newcomer.

**Architecture**

- Difficulties in integration something new.
- Hard to reuse code.
- Hard to scale an app.
- Hard to maintain.

**Team**

- Delays.
- Wrong estimations during planning.
- Demotivation.

### How to manage technical dept

- Up-to-date info about tech dept.
- Backlog.
- Tools. <Muted>Quality gate tools like SonarQube.</Muted>

**Project Statuses (RAG)**

- Red means there are issues your team needs to address for the project to be delivered successfully.
- Amber signals the project has some potential issues that your team may need to revisit in the future.
- Green indicates healthy project performance.

### Instructions to solve tech debt

**Leaders**

- Plan.
- Support and motivate your squad.
- Report TD statistic.
- Involve Stakeholders to tech debt tasks to avoid miscommunication.

**Devs**

- Code Smells.
- Code Reviews.
- Knowledge-sharing.
- Code analysis tools.
- Automated tests.
